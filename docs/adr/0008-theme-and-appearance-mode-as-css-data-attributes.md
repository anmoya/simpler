# Theme and Appearance Mode as CSS data attributes

Themes (named color/typography/shape sets, e.g. "Warm") and Appearance Mode (light/dark) are modeled as two independent HTML attributes on `.app-shell` — `data-theme` and `data-mode` — with the color/font tokens for each combination resolved purely in `styles.css` via `[data-theme="x"][data-mode="y"] { --color-*: ...; }` blocks, rather than a TypeScript theme registry that injects CSS variables at runtime. `data-theme` carries the Theme; `data-mode` carries the Appearance Mode. This matches the "Theme"/"Appearance Mode" vocabulary in `CONTEXT.md`, which asks that "Palette" not be used as a synonym for Theme, so the attribute is named `data-theme` (not `data-palette`) even though an earlier CSS-only mechanism already used the name `data-theme` for what `CONTEXT.md` now calls Appearance Mode — that older attribute was renamed to `data-mode` as part of this change rather than kept for diff size, since the mismatch between attribute name and glossary term is exactly the kind of thing that misleads a future reader.

Adding a future Theme's colors and CSS-level typography/shape means writing a new pair of `[data-theme="x"][data-mode="y"]` blocks in `styles.css` — no new component logic is needed there. Two things sit outside that CSS file and must also be touched for a genuinely new Theme: the `:root` block at the top of `styles.css`, which hardcodes the current Theme's colors and font stack as a pre-mount fallback (before `.app-shell` exists in the DOM to carry the attributes), and the `@fontsource` imports in `src/main.tsx`, which load whatever font files a Theme needs. Both are small, but they're real exceptions to "no new application logic," not resolved-away by this design.

Adding Mate Cerámico as the second Theme exercised this design and confirmed both exceptions, plus one addition. Because that Theme pairs a serif prose face with a sans UI face — a split the Warm theme does not make — `styles.css` gained a `--font-family-prose` token, defaulting to `--font-family-body` so Warm is unchanged, which `markdownEditorTheme.ts` applies to the editor surface. Component code still depends only on tokens, not on Theme names, so this stays within "no new application logic per Theme"; it does mean the set of tokens a Theme may define is not frozen, and a Theme that needs a genuinely new axis is expected to add a token with a backward-compatible default rather than branch on the Theme name. Selecting a Theme is separate from defining one: `data-theme` is fed from `AppState.theme`, persisted under `simpler.theme` exactly as the Appearance Mode is under `simpler.themeMode`.

We considered a TS-side registry of theme objects applied as inline style variables, which would allow themes defined or edited at runtime (e.g. user-authored themes). We rejected it for now: today's requirement is "support adding more Themes later," not "let users define their own," and the CSS-only approach costs the least new runtime code while fully satisfying that requirement. If runtime-defined themes become a real requirement, the registry approach remains available as a follow-up without needing to undo this one — component code only depends on the two data attributes being set, not on how the variables behind them are produced.
